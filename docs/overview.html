System Overview · fdpompeii.org

Pompeii Archaeological Field Recorder

An offline-first field recording system and expert-review pipeline for the Food And Drink in Ancient Pompeii project's excavation master sheets — from the trench wall to the approved master catalog.

Rails 8.1 API React 19 · Vite 8 SQLite + Solid Stack Docker + Kamal → fdpompeii.org GitHub Pages demo Offline-first · Service Worker

1What This Is

A monorepo containing two independent applications that digitize the paper "Pompeii Excavation Master Sheet": field archaeologists record rooms/features on site — pushing change requests in real time when connected, or queuing them for batch sync when not — submissions flow into a review queue, and admins approve or reject each one before it merges into the master catalog.

Field Client

frontend/

React 19 + Vite 8 SPA

Offline-first recording app: landing flow, master-sheet form with controlled-vocabulary pickers, photo uploader with <1 MB client-side compression, autosaved drafts, a local outbox — and a service worker that precaches the whole app.

Backend & Portal

backend/

Ruby on Rails 8.1 · Ruby 4.0.5

JSON API (/api/v1) for the field client plus a server-rendered Admin Review Portal with field-by-field diffs, inline reviewer corrections, approve/reject actions, and master catalog export.

Master Catalog

4,959

feature records (~5.9 MB JSON)

The full Pompeii dataset ships in both apps — seeded into the backend DB and bundled with the SPA as an offline fallback. Keyed by unique master-sheet number.

Core Principle

Review → Merge

Submissions are drafts, Features are truth

Nothing enters the master catalog directly. Every field submission lands in a queue; reviewers can correct fields inline, and only an explicit approval merges it in — inside a transaction, with a recorded diff.

2System Architecture

Two client surfaces, one Rails application. In production both ship in a single Docker image served same-origin at fdpompeii.org; a GitHub Pages build of the same SPA talks to the API over CORS-enabled JSON. Admins use a session-authenticated, server-rendered portal. All state lives in SQLite — no Redis, no external services.

3Domain Model

Three ActiveRecord tables plus Active Storage. The Submission payload mirrors the Feature schema, so a submission can be diffed and merged field-for-field.

ModelPurposeKey details
Feature The master catalog — one row per master sheet ever recorded. Unique sheet key; ~30 paper-sheet fields (region, insula, entrance, recorder/researcher IDs, season, description, photo/video metadata); photos as JSON in photos_data.
Submission A proposed create or update awaiting review. payload_data JSON · action_type (create_new/update_existing) · pending approved rejected · submitter & reviewer notes · Active Storage photos · grouped EDITABLE_FIELDS whitelist for reviewer corrections.
User Accounts for both surfaces. bcrypt (has_secure_password) · roles admin/recorder · full_name + display-name fallback · seeded from credentials (never the repo) · login by username or email.

4Submission Lifecycle

From the trench to the master catalog. Offline operation is a first-class path, not an error state.

1Record on siteNew sheet or an edit of an existing room (form pre-filled from the master record; draft autosaved locally); photos compressed <1 MB in-browser.
2Submit or queueConnected → pushed in real time to /api/v1/submissions. Unconnected → localStorage outbox, batch-synced later.
3Review queueSubmission stored pending; bulk sync endpoint replays offline batches.
4Diff & decideReviewer views old-vs-new per field, can correct fields inline (PATCH), then approves or rejects.
5Merge on approveTransaction upserts the Feature by sheet number, merges photo lists, stamps reviewer + time.
6Catalog refreshClients re-pull /api/v1/features; admin can export features.json anytime.

6How It Is Deployed

One production image ships both apps to fdpompeii.org via Kamal; the same SPA is also published standalone to GitHub Pages as an offline/demo build. Backend deploys are manual (bin/deploy); Pages deploys are automatic.

Production image — one container, both apps

Builds from the repo root

A node:24-slim stage builds the SPA (VITE_BASE=/ VITE_BACKEND_URL= → same-origin) and copies dist/ into the Rails app's public/, so fdpompeii.org serves field client, API, and portal from one site.

Multi-stage & hardened

ruby:4.0.5-slim + jemalloc · gems, bootsnap & assets precompiled in throwaway stages · runs as a non-root rails user · entrypoint runs db:prepare on boot.

Runtime

Thruster wraps Puma on container port 80 — HTTP/2, X-Sendfile. Solid Queue supervisor runs inside the web process. public/ is served with no-cache so the SPA shell and service worker update immediately on deploy.

Persistence

Docker volume fdpompeii_storage:/rails/storage holds the SQLite files (primary + cache + queue + cable DBs) and Active Storage uploads, surviving deploys.

Frontend & CI

GitHub Pages (automatic)

Root .github/workflows/deploy.yml builds frontend/ and publishes dist/ on every push to main touching frontend/**. Vite base is /pompeii-recorder/; built assets go to field-assets/ to avoid clashing with Rails' /assets.

Pages backend connectivity

Without the VITE_BACKEND_URL repo secret, the Pages site is a self-contained demo: offline login, bundled catalog snapshot, local outbox only. Set the secret to an HTTPS backend to wire it up (Pages is HTTPS-only). Details in frontend/DEPLOYMENT.md.

CI (backend/.github/workflows)

GitHub Actions on PRs & main: Brakeman (static security), bundler-audit (gem CVEs), importmap audit (JS CVEs), RuboCop lint. Dependabot enabled. Backend deploys are manual via bin/deploy.

Service worker

A custom Vite plugin writes sw.js with the full build precached (content-hashed). In production the app opens with zero connectivity after first visit; API/admin paths always pass through to the network.

7Observations & Risks

Open API surface

CORS allows all origins and submission endpoints require no authentication — anyone who can reach the API can queue or bulk-sync submissions. Only the admin portal is protected. The GitHub Pages demo depends on open CORS, so tightening it trades convenience for safety.

Shared recorder password

Offline login accepts any recorder via a PBKDF2-hashed shared password embedded in the client bundle, and remembers per-device logins as salted hashes. Better than the old plaintext credentials, but a shared secret can still be extracted and grants submission rights.

No API tokens

API login is one-time validation; the client keeps state in localStorage. There is no bearer token or per-request auth for the API.

localStorage limits

The outbox, form drafts, and catalog cache are per-browser and subject to quota/clearing. Mitigated by strict <1 MB photo compression and drafts that degrade gracefully when storage is full.

Pages demo mode

The GitHub Pages build runs with no backend by design: bundled catalog snapshot, offline login, outbox-only submissions. It must never be mistaken for the system of record — fdpompeii.org is.

Well-chosen simplicity

The SQLite/Solid-stack, single-container design fits an offline field project well: one box, one volume, no Redis/Postgres to babysit — one image serves SPA, API, and portal — and the review-then-merge workflow protects catalog integrity. Seed passwords now live in encrypted credentials, not the repo.
